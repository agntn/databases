A migration is a plain `.sql` file in `migrations/`. Files apply in name order. Each one runs in a single transaction together with its row in `databases_migrations`. So a file lands whole, or it doesn't land at all.

No ORM, no config file, no down migrations. Just SQL you can read.

## How do you start one?

Give it a few words. The CLI picks the next number for you.

```bash
databases migrations create "add reviews" --sql "CREATE TABLE Review (
  ReviewId INTEGER PRIMARY KEY,
  TrackId INTEGER NOT NULL REFERENCES Track (TrackId),
  Stars INTEGER NOT NULL CHECK (Stars BETWEEN 1 AND 5)
);"
```

```text
Created /var/tmp/chinook-mig/migrations/0001_add_reviews.sql
Check it, then apply it.
```

Without `--sql` you get a file with a comment, waiting for you. Pass `--sql -` to pipe the SQL in. `-d` points at another folder. An existing file is never overwritten.

## What's still pending?

`status` compares the folder with the table. It only reads.

```bash
databases migrations status chinook.db
```

```text
/var/tmp/chinook-mig/chinook.db (sqlite), migrations in /var/tmp/chinook-mig/migrations:
0 applied, 1 pending
  0001_add_reviews.sql  pending
Apply runs the pending ones in this order.
```

A database that never ran a migration has no table yet. That's fine. Everything just shows as pending.

## How do you apply them?

```bash
databases migrations apply chinook.db
```

```text
/var/tmp/chinook-mig/chinook.db (sqlite): applied 1 migration
  0001_add_reviews.sql  2026-11-19T15:54:19.827Z
```

Run it again and nothing happens. Want one step at a time? Pass `--to 0001_add_reviews.sql` and it stops there.

## What if a file fails?

Say the seed has an eleven-star review.

```sql [migrations/0002_seed_reviews.sql]
INSERT INTO Review (TrackId, Stars) VALUES (1, 5);
INSERT INTO Review (TrackId, Stars) VALUES (2, 11);
```

```text
Nothing applied, then 0002_seed_reviews.sql failed: CHECK constraint failed: Stars BETWEEN 1 AND 5 [query]
```

The five-star row is gone too. The whole file rolled back, and `Review` is still empty. Files before the failing one stay applied, files after it wait. Fix the file and apply again.

## Can you edit one that already ran?

No. Each record keeps a SHA-256 of its file. Change a single byte and apply stops.

```text
Refused: 0001_add_reviews.sql changed after it was applied. Put the old text back and write the change as a new migration [refused]
```

`status` names those files under changed. A record whose file disappeared shows up as missing.

## What about BEGIN and COMMIT?

Leave them out. The file already runs in a transaction, and its own `COMMIT` would land half of it. So a file with `BEGIN`, `COMMIT` or `ROLLBACK` is refused, and nothing from it stays. Postgres runs the file inside `EXECUTE`, so it says no to `SAVEPOINT` and `COPY` too. SQLite takes a savepoint just fine.

## Does every engine do this the same way?

Close enough.

| Engine | One file runs as |
| --- | --- |
| SQLite | `BEGIN IMMEDIATE`, the file, its record, `COMMIT` |
| Postgres | one transaction with an advisory lock, the file inside `EXECUTE`, five minutes per file |
| D1 | one `/query` batch, which D1 rolls back when a statement fails |

The Postgres lock means two deploys take turns instead of racing. D1 has no `BEGIN` at all, so the batch is what makes a file all or nothing. That's the same thing `wrangler d1 migrations apply` relies on.

## From code or from an agent?

```ts [deploy.ts]
import { applyMigrations, migrationStatus, open } from "@agntn/databases";

const shop = await open("shop");
const { pending } = await migrationStatus(shop, { directory: "db/migrations" });
const { applied } = await applyMigrations(shop, { directory: "db/migrations" });
```

`createMigration(title, { directory, sql })` writes the next file. Agents get the same three steps as `databases_migrations_status`, `databases_migrations_create` and `databases_migrations_apply`. The [agent guide](/guide/agents) lists them all.
