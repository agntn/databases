D1 reads get checked before they leave your machine. That check is useful, but its schema can briefly lag.

::provider-roster{engine="d1"}
::

## How do you point at a database?

Use `d1:<name or id>` for a database name or ID. A name is looked up once. Alternatively, use `d1://<account id>/<database>` with a 32 character hexadecimal account ID.

Set `CLOUDFLARE_API_TOKEN`, or use the `cf` CLI login. The account comes from `CLOUDFLARE_ACCOUNT_ID` or the login. If a token fetched from `cf` receives a 401, it is fetched again once.

## Why is a write refused before sending?

The package reads CREATE statements from `sqlite_schema`. It caches them for one minute and prepares your statement against an empty copy. The copy uses SQLite's authorizer in a child process.

A write, second statement or schema mismatch is refused locally. Nothing from that refused statement is sent to D1. Changed the schema a second ago? Give the copy a minute. D1's own `_cf_` tables are hidden.

## Are all integers exact?

No. The D1 REST raw endpoint returns JSON. Integers above 2^53 can lose precision in that response. Do not treat a large catalog number as exact merely because it looks plausible.
